# Decision Log

The central agent owns this file. A decision recorded here is part of the contract, and no build agent may change it.
To propose a change, add an entry to `docs/CHANGE-REQUESTS.md` and wait until it is accepted.

Status values: **Locked** (build against it), **Proposed** (waiting for Bicy's OK), **Superseded**.

| ID | Decision | Why | Revisit when | Status |
|---|---|---|---|---|
| D-001 | Run on the **Firebase Spark (free) plan** only, with **no Cloud Functions**. All business logic runs on the device, and Firestore Security Rules are the only thing enforcing it on the server. | The client should approve the product before any paid plan. | After the pilot is approved we move to Blaze. See "Blaze upgrade path" below. | Locked |
| D-002 | Stack: Flutter (Android first) for the POS app, Flutter Web for the admin console, Firestore, and Firebase Auth (email + password). One monorepo using Dart pub workspaces. | We can share models and business rules across both apps. | — | Locked |
| D-003 | **Bill number = `{LOC}-{DEV}-{SEQ}`**, e.g. `PTB-D01-000123`. Each device has its own sequence. The Firestore doc ID is `{DEV}-{SEQ}`, so it is deterministic. | Without a server we cannot allocate a single store-wide sequence that is safe offline. Per-device series never collide and have no gaps. | On Blaze, a function can assign a store-wide number (`PTB-000123`) on sync and keep the device number as a secondary reference. **This departs from BRD §4.2 and must go back into the BRD as v4.** | Locked |
| D-004 | Every app install registers as a **new device code** (D01…D99, per location), and codes are never reused. Registration requires network. | A reinstall loses the local counter. Reusing a code would produce duplicate bill numbers. | — | Locked |
| D-005 | All stock changes are written as **deltas** using `FieldValue.increment` (integers only), and every change also writes a movement record. | Concurrent offline devices merge correctly, and there is no last-write-wins. | — | Locked |
| D-006 | Quantities are integers in **base units**: raw materials in g, ml or pcs, and finished goods in pcs. Money is integer **paise**. | Avoids floating-point drift in increments and totals. | — | Locked |
| D-007 | Each sellable size is its own product (for example, "Black Forest 1 kg" and "Black Forest 500 g"). There are no variants in the MVP. | Keeps billing, stock and reports simple. | If the catalog grows past ~300 SKUs. | Locked |
| D-008 | Cakes a Store Manager suggests are created as `pending` with a proposed price. They **cannot be sold until an Admin approves them** and sets the price. | Pricing is Admin-only (BRD §3.2). | If approval turns out to be a bottleneck, auto-approve at the proposed price and let the Admin edit it later. | Locked |
| D-009 | Bills are never edited. A Store Manager can **cancel a bill on the same business day** with a reason, which restocks the items and reverses the summaries. After that day, only returns are allowed. | Summaries stay correct and every change leaves an audit trail. | — | Locked |
| D-010 | The bill total is **rounded to the nearest ₹1**, and the round-off is shown as its own line. | Common practice at the counter, so no coins are needed. | — | Locked |
| D-011 | A bill-level discount is either a flat amount or a percentage (rounded half-up to the paise). Each location has an optional `maxDiscountPct` cap, with no cap by default. | Matches BRD §4.4. The cap is optional. | — | Locked |
| D-012 | A return counts on **the day it is processed**, not on the original bill's date. | Closed days never change. | — | Locked |
| D-013 | **No GST in the MVP.** The data model includes `gstRate` on products and `taxLines` on bills, both empty for now. The printer prints the GST block only when `taxLines` is non-empty. | Flat bills for the pilot, as agreed. | When GST is enabled. | Locked |
| D-014 | Reports read **pre-aggregated summary docs** (daily and monthly per location), which are incremented in the same write batch as the bill, return, cancellation or expense. | Without Functions, this keeps admin reads cheap enough for the Spark quota. | — | Locked |
| D-015 | Low-stock alerts are **computed in the app** from the stock docs and shown as an in-app badge and list. **No push notifications** in the MVP. | Server-side push needs Functions (Blaze). | Blaze: an FCM push from a Firestore trigger. | Locked |
| D-016 | Offline limit: a warning at 80% of the location's `offlineLimitHours` (default 5), and **new billing is blocked** at 100%. An **Admin override PIN** (per store) allows billing until 2 hours from the moment it is entered (`overrideExtensionHours`), however long the device has been offline. The override is audited and can be repeated. | BRD §7. The block-or-warn question is now settled as "block, with a PIN override". | — | Locked |
| D-017 | Roles are data (`roles/{roleId}.permissions[]`), and both the rules and the UI check permissions, never role names. | BRD §3 note: a Cashier role should be addable later without rework. | — | Locked |
| D-018 | Admin creates Store Manager logins from the web console through a **secondary Firebase App instance**, so the Admin session isn't replaced. Disabling a user sets `active=false`, and the rules then deny every operation for that user. | Without the Admin SDK, we can't create other users any other way. | Blaze: move to a callable function with the Admin SDK and custom claims. | Locked |
| D-019 | Audit entries are written **in the same batch** as the change, with the same ID. The rules use `existsAfter()` to require that the audit entry exists. Audit docs are create-only. | Audit on the server without Functions. | — | Locked |
| D-020 | Printer paper width is **80 mm (48 columns)** by default, with 58 mm (32 columns) configurable per device. Connection is Bluetooth Classic SPP with ESC/POS. | "Slightly larger than a petrol-pump slip". | After hardware testing with the pilot printer. | Locked |
| D-021 | Cold-storage backup and data retention are **out of the MVP**. Scheduled Firestore export needs Blaze. | One pilot store stays well under the free storage limit. | Blaze. | Locked |
| D-022 | Business date = the device's local date in IST (`Asia/Kolkata`), stored as `YYYY-MM-DD` next to `serverCreatedAt`. | Summaries need a stable day key that works offline. | If clock tampering shows up, compare it against `serverCreatedAt` in reports. | Locked |
| D-023 | POS Android application ID is **`in.caramelcottage.pos`**, matching the `caramelcottage.in` domain. The Kotlin code package (`namespace`) stays `com.caramelcottage.pos`, because `in` is a Kotlin keyword; only the application ID is visible to Firebase and Play. Workspace package names carry a `nexus_` prefix (`nexus_core`, `nexus_data`, `nexus_printer`, `nexus_pos`, `nexus_admin`, `nexus_e2e`). | The application ID is registered with Firebase in B-5 and on Play later, and can't change after that. | Never, once B-5 is done. | Locked |
| D-024 | **Money arithmetic.** (a) One rounding rule everywhere: to the nearest paisa or rupee, halves away from zero (₹10.50 → ₹11). (b) A percentage discount is `subtotal × pct / 100`, rounded; the location cap applies to flat discounts too, measured as a share of the subtotal. (c) A bill's net amount (`total − roundOff`) is split across its lines by largest remainder, so the parts add up exactly. `byProduct.amount` records this per-line net, and returns prorate from it. (d) Returns are **cumulative**: each return refunds the value of everything returned so far minus what was returned before, for line amounts and for the rupee-rounded `refundTotal`. (e) A bill has at most one line per product. (f) Movement and return IDs pad the sequence to 6 digits like bills: `D01-M000042`, `D01-R000007`. | Rounding each partial return on its own can over-refund by up to ₹1 per return, and per-product totals wouldn't reconcile with net sales. With (c) and (d), a bill's refunds always add up to exactly its total and never exceed it. One return's `refundTotal` can differ from the sum of its line amounts by less than ₹1. `returnedQty` is keyed by product, so (e) keeps it unambiguous. | If GST needs per-line tax rounding. | Locked |
| D-025 | A bill that has any return **can't be cancelled**, even on the same day. The remaining items can still be returned. | Cancelling reverses the whole bill, so the part already refunded would be reversed twice in stock and in the summaries. | If Store Managers need to undo a return itself. | Locked |
| D-026 | The apps talk to data and printing **only through interfaces**: `packages/data/lib/src/api/` (auth, device, catalog, sales, stock, reports, admin, sync, offline guard) and `packages/printer/lib/src/api.dart` (`PrinterService`). The central agent owns these files. The backend and printer agents implement them, and the apps never import `cloud_firestore` or a Bluetooth plugin directly. | The POS and admin agents can build and test against fakes from day 1, in parallel with the backend. Integration is then a swap of implementations, not a rewrite. | — | Locked |
| D-027 | Batch builders return a pure **`WritePlan`** (ordered creates, updates and merges, with increment and server-timestamp sentinels), and a thin adapter applies it to a `WriteBatch`. Plans are exported as JSON fixtures, and the Node rules suite applies them to the emulator. | Business rules become unit-testable with `flutter test`, which can't reach the emulator, and the rules are tested against exactly the writes the app makes. | — | Locked |
| D-028 | Audit IDs of location-scoped events are **`{loc}-{entityId}`** (`Ids.auditId`), e.g. `PTB-D01-000123-X`. Offline overrides are `{loc}-{deviceId}-OVR-{millis}`. | `auditLog` is one root collection and device codes repeat across locations, so an unprefixed ID from MNJ's `D01` would collide with PTB's and be rejected for good (QA-001). | — | Locked |
| D-029 | **Conflicting offline writes: first to sync wins.** The rules deny a cancel once a bill has any return, a return once it is cancelled, and any `returnedQty` above the bill's `soldQty`. `returnedQty` changes only with a new return doc (`lastReturnId`), and only if that return was worked out from the bill's current state (`prevReturnId` equals the bill's `lastReturnId`). The losing batch becomes a sync error. | Without it, two offline devices could refund one bill twice or beyond its total (QA-002, QA-003). Returns and cancellations stay possible offline. | If sync errors from this show up in the pilot, require network for returns and cancellations. | Locked |
| D-030 | **List limits:** at most **15 lines per bill** (and so per return), 20 lines per movement, 4 payments per bill and 4 refunds per return (`Limits` in core). | The rules can then check every line without loops and stay within Firestore's access-call budget (QA-010) and its 1000-expression limit per evaluation, with about 25% headroom (CR-001). A cake-shop bill rarely has more than a handful of lines. | If the pilot hits 15 lines on a bill. | Locked |
| D-031 | **Client-enforced rules, accepted for the pilot:** unsellable products (D-008), the same-day cancel check (D-009), the device clock, the offline-guessable override PIN (minimum 8 digits), stock always changing by increment rather than a literal `qty` (D-005, kept by the plan builders), and a return's lines matching its `returnedQty` increase. | The rules can't check these within budget or without a server. They're listed in 04-PERMISSIONS so nobody assumes the server enforces them (QA-007, QA-014, QA-022). | Blaze: move them to Functions. | Locked |
| D-032 | **One audit-ID builder per action**, all in `Ids`. Location-scoped events are `{loc}-…` with `locationId` set: cancellations, returns, wastage and adjusts (`auditId`), overrides (`overrideAuditId`), expenses `{loc}-EXP-{id}-{millis}`, location updates `{loc}-LOC-{millis}`, and users with a location `{loc}-USR-{uid}-{millis}`. Global events have `locationId` null: `PRICE-{productId}-{millis}`, `APPROVE-{productId}-{millis}`, and users without a location `USR-{uid}-{millis}`. Every action needs its own permission, at the location when scoped. Adds `USER_ENABLE`. `THRESHOLD_CHANGE` is reserved and not written in the MVP. | Two workers had invented different IDs for the same event, and a null `locationId` let one store pre-empt another store's audit IDs (QA-037, QA-041, BE-CR-1, DA-CR-1). | — | Locked |
| D-033 | **A device code is only valid at the location it was registered at.** `DeviceService.locationId` records it. When the signed-in user's location is different, the POS treats the install as unregistered and registers a new code at that location (D-004: codes are never reused or moved). | Otherwise a phone registered at PTB, signed into by an MNJ Store Manager, would bill at MNJ under PTB's code and collide with MNJ's own device of the same code. | — | Locked |
| D-034 | **Every bill carries the customer's name and mobile number. The WhatsApp number is only needed when it differs from the mobile.** The form has a switch, "WhatsApp is the same number", on by default. Three outcomes: the mobile is also on WhatsApp (the switch stays on, `customerWhatsapp` = `customerPhone`); a different number is on WhatsApp (the cashier types it); the customer isn't on WhatsApp (the switch is turned off and the field left blank, `customerWhatsapp` = null, and the WhatsApp buttons are hidden for that bill). Fields on the bill: `customerId` (D-037), `customerName` (1–60 chars, trimmed), `customerPhone` (10 digits, starts 6–9, India only), `customerWhatsapp` (same shape, or null). The printed receipt shows the name only, never the number. Rules reject a new bill without a valid name and phone. | Bicy's pilot feedback: the shop wants to reach buyers on WhatsApp, and not everyone is on it. Required name and phone were chosen by Bicy over the optional version, so expect some junk numbers at a busy counter: validation can only check the shape. | After the pilot: if junk numbers are common, make the number optional for small walk-in bills. | Locked |
| D-035 | **Review, then submit; print and share are optional follow-ups.** The POS shows a read-only review (customer, lines, discount, round-off, total, payments) before the bill is committed, with Back to edit and Confirm. The review is **on by default**. The cashier can tick "Don't show this review again" on the review screen, and can turn it back on in **Settings → Review bill before saving**. The choice is kept on that phone, per signed-in user. With the review off, Confirm saves the bill straight away. After the bill is saved the cashier chooses Print, WhatsApp, both or Done. The bill is committed once, and print or share never create or change a bill (D-009). | Catches mistakes before a number is consumed (a bill can't be edited, only cancelled the same day). A fast counter can switch it off. A bill with no print is allowed, so a printer fault never blocks a sale. | If cancelled bills turn out to come mostly from skipped reviews. | Locked |
| D-036 | **WhatsApp sharing is done on the phone, with no server.** Two options after a bill is saved: (a) a `https://wa.me/91<number>?text=<receipt text>` link that opens WhatsApp with the customer's chat and the plain-text receipt already filled, and the cashier presses Send; (b) the receipt as an image through the Android share sheet, where the cashier picks the chat (the contact can't be preset). Neither is automatic, and neither is recorded as "sent". Automatic sending needs the WhatsApp Business API and a server (Blaze). | D-001 rules out a server. The link is free and keeps the number the shop captured. | Blaze: a template message sent from a function. | Locked |
| D-037 | **Customers are stored, one record per mobile number and name, in each location.** `locations/{loc}/customers/{customerId}` with `customerId = {phone}_{nameKey}`. `nameKey` is the first 10 hex characters of the SHA-256 of the name after trimming, collapsing spaces and lower-casing, so the ID is deterministic offline and works for any script. The same mobile with a different name is a different customer (for example, two people sharing a phone). Fields: `name`, `phone`, `whatsapp` (the latest used, or null), `lastBillAt`, `billCount` and `totalSpend` (both as billed, like `grossSales`, with cancellations not reversed), `lastWriteRef`. Every bill's batch writes the customer with `set(merge)`, since offline a device can't tell whether it exists: the same `name` and `phone`, `whatsapp` and `lastBillAt` overwritten, and the two counters incremented (the summary pattern, with `lastWriteRef` naming the bill). While billing, typing a mobile number offers the saved names for that number (from the local cache, so it works offline) and fills the form. The Admin sees all locations' customers (read only); a Store Manager sees their own location's. The rules can't compute the hash, so they check the ID's phone part against the bill and the length, and the `nameKey` is client-enforced (D-031 style). A different spelling of the same name makes a second record, which is accepted for the pilot. A change of letter case only (the same `nameKey`) is allowed by the rules and the stored name takes the latest spelling, because refusing it would lose the whole bill when it syncs. | Bicy asked for customers to be stored, identified by mobile and name. Per location, not shared, keeps the cross-location isolation rule (a manager must not read another store's data); the Admin still gets the whole list. | Blaze (a function can merge duplicates), or if the shop wants one shared customer list across stores. | Locked |
| D-038 | **A Store Manager is told about the Admin's decision on a suggestion inside the app, with no push (D-015).** A "My suggestions" list on the POS shows each suggestion's status (Pending, Approved with the price, or Not approved with the note). When a status has changed since the manager last looked, the Stock/Menu entry shows a dot, and the next time the app is open or comes online a banner says "Black Forest 1 kg was approved at ₹X". The product gains `reviewedAt`, `reviewedBy` and `reviewNote` (the reason when declined; a declined suggestion is `INACTIVE` with a note). "Last seen" is kept on the phone. | The manager had to scan the whole catalog to find out. A real push needs a server (Blaze). | Blaze: an FCM push when the Admin decides. | Locked |
| D-039 | **Negative finished-goods stock is normal when cakes are sold without a recorded PRODUCE, and sales are never blocked by stock** (03-SYNC §3). The Stock screen lists raw materials and finished goods together, and gets a Finished / Raw filter beside All / Low stock. A new **Stock history** screen lists movements with an In / Out / All filter and a date, so "stock in only" and "stock out only" can be seen. | A cake sold at 0 shows -1 in red until a PRODUCE or Adjust brings it back. The Admin's goal is to count what's physically on the counter. | If negative stock turns out to hide real shortages: show a non-blocking warning at the point of sale. | Locked |

## Blaze upgrade path (after approval)

1. Store-wide bill numbers are assigned by a Firestore trigger (D-003).
2. Push notifications for low stock (D-015).
3. User management through a callable function with custom claims (D-018).
4. A scheduled export to Cloud Storage for cold backup (D-021).
5. Summaries recomputed on the server, as a cross-check against the client-written ones (D-014).

None of these steps change the data model. They add server writers alongside the client writers.
