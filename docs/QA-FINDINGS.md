# QA Findings

Owner: QA. One row per finding, as `QA-nnn | branch | priority | what | where | expected`. `branch` is `main` for findings against the contracts themselves (docs, `packages/core`, `packages/data/lib/src/api/`).

Priorities: **P1** data loss, wrong money, a security hole or a broken acceptance item (blocks the merge); **P2** a contract gap or contradiction that will make an implementation or a test guess; **P3** minor gap or wording that leaves a result undefined.

All rows below are open. The central agent records the outcome of each, and QA closes a row once the contract and a scenario in `test/e2e/PLAN.md` agree.

| QA-001 | main | P1 | Audit doc IDs collide across locations. `auditLog` is a root collection and an audit ID is the entity's ID (`D01-000123-X`, `D01-R000007`, `D01-M000042`), but device codes are per location (D-004), so PTB `D01` and MNJ `D01` produce the same audit IDs. Audit docs are create-only, so the second location's cancel, return, WASTAGE or ADJUST batch is rejected for good (a sync error). A cancel ID is derived from the bill ID, so MNJ bill `D01-000123` can never be cancelled once PTB's `D01-000123` was. | 02-DATA-MODEL `auditLog/{auditId}`; 04-PERMISSIONS #10; D-019; `Ids.cancelId` ("the CANCEL movement and the cancellation audit doc") | Audit IDs include the location, e.g. `PTB-D01-000123-X`, with an `Ids.auditId(loc, entityId)` builder in core, and rule #10 checks `existsAfter(auditLog/{loc}-{id})`. Scenario A1-5. |
| QA-002 | main | P1 | A cancel and a return of the same bill can both be accepted. D-025 forbids cancelling a bill with returns, but rule #5(a) doesn't check `returnedQty`, and rule #5(b) doesn't require `status == COMPLETED` for a `returnedQty` increment. Two devices offline the same day (one cancels, one returns part of the bill) both sync: the customer is refunded twice, stock is re-credited twice, and the summary subtracts both `cancelled` and `returns`. | 04-PERMISSIONS #5; D-025; 03-SYNC §2 | Rule #5(a) requires no returns (e.g. `returnedQty` is empty, which means the return path never writes zeros) and rule #5(b) requires `resource.data.status == 'COMPLETED'`; whichever lands second becomes a sync error (03-SYNC §6.3). Scenarios R-5b, R-5c, M-5. |
| QA-003 | main | P1 | Over-return isn't enforced on the server. "`returnedQty[p] + qty ≤ sold qty`" is a client check only; rules can't loop over `lines` to find the sold qty. Two devices offline each return the last unit of the same line; both sync and the bill is refunded beyond its total, breaking D-024's "never exceed" guarantee. Rule #5(b) also doesn't tie the increment to a new return doc, so `returnedQty` can be raised with no return at all. | 02-DATA-MODEL returns ("Before creating a return, the client checks…"); 04-PERMISSIONS #5(b); D-024 | Store a `soldQty` map (productId → qty) on the bill at creation, and have rule #5(b) require, for each changed key, `request.resource.data.returnedQty[p] <= resource.data.soldQty[p]` (the rule sees the value after the increment) plus `existsAfter` of a new return doc. Scenarios R-5c, M-6. |
| QA-004 | main | P1 | Stock docs can't be created safely offline. The model says a stock doc "is created with `qty: 0` and `set(..., merge: true)` the first time an item is used" and rule #8 allows create only with `qty == 0`. (a) If the first use is a sale or a return, the batch must create the doc with a non-zero qty (an increment on a missing doc), which rule #8 denies, so the bill is lost. (b) Whether it's the "first time" is decided from the local cache; an offline device without the doc cached writes `qty: 0` with merge onto a doc another device already created, which resets its qty, and rule #8 allows it because a movement exists in the same batch. Either way D-005 breaks. | 02-DATA-MODEL `stock/{itemKey}`; 04-PERMISSIONS #8; D-005; 03-SYNC §5 | Batches never write a literal `qty`: always `set(merge)` with `qty: increment(delta)`, and rule #8 allows a create whose `qty` equals that item's delta in the named new movement, or stock docs are created up front (on product approval / material creation / location creation) by an online operation. Scenario S5-5. |
| QA-005 | main | P1 | No rules contract for `locations/{loc}/devices/*`. The bill batch updates `devices/{id}.lastBillSeq` (with `bill.create`), the sync pass updates `lastSeenAt`, registration creates the doc (with `device.register`), and the Admin retires it. Rule #4 only covers the location doc ("writable only with `location.manage`"). Read literally, every bill batch is denied; written loosely, any SM can overwrite any device doc at the location. | 04-PERMISSIONS #4; 03-SYNC §2, §3, §6; BE-2 scope | A device rule: create with `device.register` only at code `D{nextDeviceNo}` and only if it doesn't exist; `lastBillSeq` only with `bill.create`, set to the new bill's `seq` and never lowered; `lastSeenAt` by any user at the location; `label`/`retired` with `location.manage`. Scenarios A1-3, R-4, S6-4. |
| QA-006 | main | P1 | Device codes can be reused. `LocationService.save(Location)` takes the whole `Location`, including `nextDeviceNo`, and rule #4 lets `location.manage` write every field. An Admin editing a location while a device registers writes back a stale `nextDeviceNo`; the next registration gets a code that already exists, and two installs bill as the same device (duplicate bill IDs, rejected batches). It's also unspecified whether the new device is `D{old value}` or `D{new value}` and what a new location's `nextDeviceNo` starts at, which the seed script and the Admin console must agree on. | `packages/data/lib/src/api/admin.dart` `LocationService.save`; 04-PERMISSIONS #4; 02-DATA-MODEL `nextDeviceNo`; D-004 | `LocationService.save` never writes `nextDeviceNo` (the rules deny any change to it except +1 by `device.register`, even for Admin), device create requires `!exists`, and 02-DATA-MODEL states the start value and which value the new code uses. Scenario A1-3. |
| QA-007 | main | P2 | The same-day cancel rule isn't enforced by the server. Rule #5 checks `businessDate == cancel.businessDate`, but both values are written by the client, so a cancel a week later passes by writing the bill's own date into `cancel.businessDate`. BE-3's "next-day cancel (denied)" can only be tested as a client writing an honest later date. | 04-PERMISSIONS #5(a); D-009; 06-TASKS BE-3 | Either state that D-009 is client-enforced only (the rule just keeps the two dates consistent), or add a server bound on `request.time` against the bill's `serverCreatedAt` (loose enough to accept a same-day cancel that was queued offline and syncs later). Scenarios R-5b, M-5. |
| QA-008 | main | P2 | Rule #8 doesn't require the movement to be new. A qty change only needs `existsAfter` of the movement named in `lastMovementId`, so a later write can change `qty` by any amount while naming an old movement: stock changes with no movement and no audit doc. Rule #9 closes the same hole for summaries with `!exists`. | 04-PERMISSIONS #8 vs #9 | Rule #8 also requires `!exists(movement)` before the batch, as #9 does. Scenario R-8. |
| QA-009 | main | P2 | Read access is unspecified for stock, movements, devices, bills, returns and summaries. The rules list only covers reads for `roles`, `users`, `locations`, `auditLog` and `products`; the catalogue gives `report.own` "summaries, bills and returns" but no permission to read stock (POS stock hub, low-stock badge), movements or devices (Admin device list), and nothing says whether `report.all` or `location.manage` covers other locations' stock for the Admin low-stock list. | 04-PERMISSIONS catalogue and rules #1–13 | A read rule per subcollection, naming the permission (e.g. stock and movements readable with `stock.move` or `report.own` at the location; devices with `device.register`; all of it with `report.all`). Scenarios A3-1, R-1. |
| QA-010 | main | P2 | The rules access budget isn't testable as written. 04-PERMISSIONS says the limit is 10 `get()`s per evaluation and "the largest batch is a return", but no contract caps the number of lines on a bill, a return or a PRODUCE / STOCK_IN movement, so there is no largest batch; each extra line adds a stock doc whose rule calls `existsAfter`. (Firestore documents 10 access calls per single-document request and 20 per batch or transaction, so the stated figure is also off.) | 04-PERMISSIONS "Rules — required helper functions"; 06-TASKS BE-6; `BillCalculator` | A maximum line count per bill and per movement (enforced in `BillCalculator` and the stock service, and by `lines.size()` in the rules), the correct Firestore limits, and BE-6 testing a bill, a return and a PRODUCE at that maximum. Scenario R-14. |
| QA-011 | main | P2 | What the PIN override grants is contradictory. D-016 and acceptance #6 say it "grants 2 more hours"; 03-SYNC §7 says "`lastSyncAt` is treated as extended by `overrideExtensionHours`". These differ once the device is past the limit: after an overnight 10 h without network, extending `lastSyncAt` by 2 h leaves `elapsed` at 8 h, so billing stays blocked until three overrides. | D-016; 01-MVP-SCOPE acceptance #6; 03-SYNC §7; `OfflineGuard.override` | Define it as "billing allowed until `now + overrideExtensionHours`" (or state the extension semantics explicitly and change D-016's wording). Scenarios A6-4, A6-9. |
| QA-012 | main | P2 | When `lastSyncAt` moves is undefined. 03-SYNC §6.4 sets it "on success", but not whether a pass that found a rejected doc (a sync error) is a success, nor its value before the first pass after registration. If a sync error blocks `lastSyncAt`, one rejected write (e.g. a disabled user's) stops all billing 5 hours later even though the device is online. | 03-SYNC §6, §7; `SyncService.lastSyncAt` | `lastSyncAt` = the end of the last pass in which `waitForPendingWrites` completed and every ledger entry was resolved (confirmed or moved to errors), and it is set by the first sign-in or registration. Scenario A6-8. |
| QA-013 | main | P2 | Cancellations leave `billCount`, `grossSales`, `discounts`, `roundOff` and `netSales` untouched (`SummaryDeltas.forCancel`), yet 02-DATA-MODEL defines `netSales` as "Σ total of completed bills". So a report's "gross vs net" and "discounts" include cancelled bills while `netRevenue`, `byMode` and `byProduct` exclude them, and "the admin's daily totals equal the sum of the bills" (acceptance #5) has two readings. P-01 currently asserts the implemented meaning. | 02-DATA-MODEL summaries; `packages/core` `SummaryDeltas.forCancel`, `Summary.netSales`; 01-MVP-SCOPE acceptance #5; AD-8 | Either reverse those fields on cancel (and drop `cancelled` from `netRevenue`), or reword `netSales` as "Σ total of bills created that day, including ones cancelled later" and state which figures reports must show net of cancellations. |
| QA-014 | main | P2 | The Admin override PIN can be recovered by any Store Manager. The PIN is the only thing standing between the SM and the offline block. | 02-DATA-MODEL `overridePinHash`; 03-SYNC §7; 04-PERMISSIONS #4 | State a minimum PIN length (e.g. 8 digits) enforced by `LocationService.save`, and record the offline-guessable hash as an accepted pilot limitation next to the clock one in 03-SYNC §7. |
